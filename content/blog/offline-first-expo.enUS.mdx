Building an app that works without internet seems like a caching problem. It isn't. It's a **distributed consensus** problem with a client that disappears for hours and comes back thinking it's right.

This post is a summary of what I learned building the offline layer for AgroCRM, where field technicians spend the entire day on farms with no signal.

## The mistake everyone makes first

The first version is always like this: save to `AsyncStorage`, set a `synced` boolean flag, and when the network comes back send everything to the server.

```ts title="lib/sync.ts" {8-10}
type Record = {
  id: string;
  data: unknown;
  synced: boolean;
};

async function sync(records: Record[]) {
  for (const record of records.filter((r) => !r.synced)) {
    await api.post("/records", record);
  }
}
```

The three highlighted lines concentrate all the problems. It's serial, doesn't handle partial failure, and assumes the server is the single source of truth.

This works on the happy path and breaks on every other. What happens when:

- The same record was edited on the phone **and** on the server?
- The `POST` timed out but the server processed it?
- Two devices from the same user sync at the same time?

## Three decisions that solve 90% of cases

### 1. The client generates the ID

Letting the server generate the ID forces you to have two states: "created locally" and "truly created". With a client-generated UUID, a record is born with a definitive identity.

```ts title="lib/record.ts"
import { randomUUID } from "expo-crypto";

const record = {
  id: randomUUID(),
  createdAt: new Date().toISOString(),
};
```

This also makes the `POST` **idempotent**: resending the same record after a timeout doesn't create a duplicate, because the server upserts by primary key.

### 2. Operation queue, not state queue

Syncing the _final state_ of a record loses information. Syncing the _operations_ preserves the intent.

| Approach | Edited name and then phone | Server result |
| --- | --- | --- |
| State queue | 1 record with both fields | Overwrites concurrent edit |
| Operation queue | 2 independent operations | Merges field by field |

In practice, each item in the queue looks like this:

```json title="queue-item.json"
{
  "op": "update",
  "entity": "visita",
  "id": "9f1c...",
  "field": "telefone",
  "value": "+55 19 99999-0000",
  "at": "2026-07-21T14:03:00.000Z"
}
```

The `field` is what allows the merge. Without it, you only know that the record changed, not what changed.

### 3. Last-write-wins per field, not per record

> Entire record conflict is a lazy decision that always discards someone's work.

Storing a timestamp per field costs a few bytes and avoids support's most annoying question: "where is the change I made yesterday?".

## Where the complexity really lives

It's not in the algorithm. It's in **observability**. When a technician calls saying they lost data, you need to answer in minutes, not days.

What saved the project:

1. Local log of every operation, with timestamp and result
2. A hidden button that exports this log
3. Metric for how many items are in the queue, visible right in the app

To inspect the queue of a device in the field, the flow is always the same:

```bash
adb shell run-as com.dolphin.agrocrm cat databases/queue.db > queue.db
sqlite3 queue.db "select op, entity, field, at from queue order by at desc limit 20"
```

None of this is glamorous. All of this is what makes the feature reliable.

## What I would do differently

I would start with the sync layer, not the UI. Offline modeling leaks into absolutely everything: schema, navigation, loading states, error screens. Treating this as "we'll deal with it later" guarantees an expensive refactor.

If you want to see this in practice in open source, [AstroVista](https://github.com/FernaandoJr/astrovista) has a much simpler version of the same idea.
